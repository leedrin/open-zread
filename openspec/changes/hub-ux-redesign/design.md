## Context

Hub 是 Windows 优先的 Tauri + React 桌面应用。当前 `apps/hub/src/App.tsx` 将首页搜索、运行诊断、项目卡、Reader 和任务面板放在一个纵向页面；`OpenZreadReader.tsx` 将阅读、问答、编辑、创建、历史和审核表单放在同一组件。已有 `HubApplicationService` 提供项目、健康状态、搜索、双 Provider 阅读、任务、问答、正文 ChangeSet、创建/删除/元数据和历史操作。正文 ChangeSet 有 `before`/`after`/`relativePath`，而创建、删除与元数据目前使用直接写入接口。基线（Windows 开发环境）：Hub TypeScript 检查通过，Bun 前端测试 27 项通过，Rust 单元测试 36 项通过。

现有阅读状态只保存在 React state 中；项目上次打开时间来自项目服务，但打开 Reader 不保证刷新它。搜索结果有项目/Provider/slug/snippet，没有字符偏移；任务服务提供本次进程内活动任务事件，没有持久历史查询。Hub 尚无通用偏好存储。结构写入路径比较 Catalog 原始字节并尝试回滚；正文 ChangeSet 暂存在进程内，应用前复核页面路径和正文。OpenZread 结构变更会记录快照，Zread 依靠 Provider 版本目录；这些路径必须继续由现有历史/修订约束保护。

本设计以 [UX 改造方案及图片](../../../docs/design/Hub_UX_Redesign_v0.1.md) 为视觉和布局参考，以 [首版功能需求](../../../docs/PRD/Open_Zread_Hub_Functional_Requirements_v1.0.md) 的 D03、D16、FR-05、FR-13、FR-17～19 为行为约束。图片中的虚构账号、任务数值、源文件路径和可选快照控件不构成真实功能要求；历史保护按既有产品约束执行，不交给用户关闭。

## Goals / Non-Goals

**Goals:**

- 用户从首页或项目库进入独立项目视图，阅读位置和返回位置稳定。
- 用户在同一个项目工作区阅读两种 Wiki、查看关联源码、搜索并直达页面；两个 Provider 的会话互相隔离。
- 编辑维护以草稿、差异预览、确认写回和结果反馈为明确步骤；任何正式文件写入仍受修订检查、串行化与历史保护约束。
- 样式、窗口宽度、焦点和状态反馈有统一规则；当前已有功能在新入口保持可达。

**Non-Goals:**

- 在线仓库发现、云账号/订阅、第三个 Provider、完整 IDE、模型能力重做或改变 CLI 行为。
- 由图片上的样例数据推断新后端指标；首页不会凭空显示响应耗时、磁盘占用或缺少依据的新鲜度。
- 对两个 Provider 的同名页面自动对齐；原文件写回、历史与冲突策略不改为 Overlay。

## Decisions

### 1. 显式视图状态与两层导航

以类型化导航状态表示 `home`、`projects`、`search`、`tasks`、`providers`、`settings`、`project-overview`、`project-wiki`、`project-source`、`project-maintenance` 和 `review`。状态包含稳定的 `projectId`、`provider`、`slug` 和返回目标，不在组件之间传递本地绝对路径作为导航键。全局侧栏与项目章节栏各有一层选中态；应用顶栏保留项目面包屑。Wiki 的 Provider 切换、新建页面、历史恢复和问答入口与项目导航共用一行，位于导航右侧；导航下直接进入章节树/文章，不显示独立 Reader 标题卡或冗余空白工具区。Wiki 阅读视图不常驻与项目设置重复的路径、可用状态、打开目录等项目摘要信息。

选用可测试的轻量导航控制器和历史栈，初期不引入额外路由依赖。搜索结果通过同一个 `openWiki(projectId, provider, slug)` 动作定位；窗口返回动作和面包屑恢复来源视图。文章标题锚点由 Reader 自己管理。项目视图容器取消上下留白并锁定为工作区高度，Wiki 导航下一行直接是章节树和文章；初次挂载时等待导航工具栏目标就绪，不显示会造成布局跳变的独立回退工具栏。替代方案是让各区块继续靠页面滚动定位，无法可靠保存“返回搜索结果”的上下文；另一方案是直接加完整浏览器路由，当前单窗口桌面应用暂不需要外部 URL 语义。

项目卡始终以打开项目为主动作，打开 Wiki 是项目内动作。项目库筛选、滚动位置和搜索结果缓存于应用会话；最近项目/阅读位置以本地偏好保存。偏好仅保存稳定 ID、Provider、slug、滚动值及时间，不保存 Markdown 草稿、密钥或绝对路径；读写失败降级为本次会话状态。收藏仍以项目服务为准。

### 2. 数据只展示真实可用状态

首页的最近项目基于本应用实际打开记录排序；收藏读取项目注册表。最近阅读由独立的项目/Provider 会话记录形成。任务入口展示当前已知的活动和排队任务以及真实事件；若未提供可恢复的历史任务列表，不显示伪造的历史记录。Provider 页面使用 `getHealth()` 的当前结果，将可用性与诊断分层展示；健康检查失败不遮蔽已保存 Wiki。

保留现有 `HubApplicationService` 作为 UI 边界。仅在项目跳转、会话持久化或维护预览确有缺口时扩展 `hub-contract` 与 Tauri 命令。另一方案是在前端推导或编造所有状态，会造成图上好看但与真实运行不符。

### 3. Reader 拆为稳定的阅读布局与互斥上下文面板

项目工作区的宽屏布局为 240px 全局导航、220–240px 章节栏、弹性文章区及打开时 320–360px 上下文面板。章节树和文章各自滚动；正文限制理想行宽。面板使用单一 `activePanel` 状态：`ask`、`source`、`metadata`、`history` 或 `none`，互斥打开。进入编辑/审核状态时面板关闭，未保存草稿受到离开保护。宽度 1100–1439px 可收起全局导航，960–1099px 将章节栏和上下文面板改为覆盖抽屉。文章至少保留可读宽度，不通过全局 `min-width: 960px` 强制横向滚动。

每个 `projectId + provider` 分别保存最近 `slug`、章节展开和滚动位置。切换 Provider 只恢复目标 Provider 的会话；原页面已删除时显示概览/说明，不按标题相似度跳转。搜索结果携带明确 `slug` 时属于用户发起的直达导航，可覆盖该 Provider 的上次阅读位置。替代方案是自动匹配同名标题，与既定 D16 决策冲突。

项目“代码”入口首轮承载现有受限的关联源文件只读查看，不呈现完整文件浏览器；源文件引用可以打开面板并返回文章。单页读取失败与整份 Wiki 不可用应是不同状态。

Wiki 正文保留本地资源读取和内部链接行为；表格解析支持 GFM 分隔行与列对齐，表格在窄文章区内可横向滚动。`mermaid` fenced code block 通过本地打包的 Mermaid API 生成 SVG，采用严格安全配置；解析失败时显示原始源码和局部错误，不影响文章其余内容。

### 4. 写入操作共用审核入口，保留底层安全边界

手动正文编辑和 AI 改写复用现有 `previewWikiChange` / `applyWikiChange`。新建、删除、移动及元数据操作目前通过 `createWikiPage`、`deleteWikiPage`、`updateWikiPageMetadata` 直接写入；实现此变更时先将这些操作改为“准备变更 → 审核 → 应用”的最小契约，预览返回受影响文件、目标修订、校验结果与前后差异，并复用现有写入逻辑，不复制第二套文件算法。多文件操作展示逐文件差异与统一结果。若某操作尚无可靠预览，界面不得冒充已生成 ChangeSet 或提前展示“可安全写入”。

审核入口显示项目、Provider、目标文件、受影响页面、差异、验证结果和“直接写回原始 Wiki 文件”的提示。只有校验成功、修订未过期时允许确认；真正应用前由后端重新检查外部改动和版本指针。历史快照由底层强制执行，不作为可取消选项。写入成功后刷新当前 Wiki、目录与搜索状态，回到原章节；冲突或失败保留草稿和审阅上下文，提供重新核对/返回编辑。放弃草稿不写正式文件。

这保持 [FR-13](../../../docs/PRD/Open_Zread_Hub_Functional_Requirements_v1.0.md) 的统一 ChangeSet 目标。只在前端放一个确认对话框然后调用直接写入接口虽容易实现，但无法显示真实差异与修订状态，也不能满足变更审核图的承诺。

### 5. 设计 token 与交互标准

Wiki 章节树使用清楚的文字层级：分组标题采用中性辅助色与中等字重，页面标题采用正文级字号，选中项使用浅薄荷底色和品牌色，折叠操作使用线性箭头图标。可读状态不在每个页面标题旁重复显示，仅对不可读页面给出明确状态。

提取颜色、字体、间距、圆角、按钮、焦点、状态与层级 token，再建导航、项目卡、状态标记、抽屉和差异视图。基准背景接近 `#FCFBF8`，品牌青绿接近 `#00B0AA`，细边框接近 `#E5E7EB`；以 Windows 字体回退和实际对比度测试调整。图标使用统一线性风格，可复用现有 SVG 或选用轻量图标库；不要求复制 Zread 商标。状态不能只靠颜色区分。

优先为应用导航、全局搜索、Provider 切换、章节树、上下文面板、审核步骤提供键盘路径；面板具备焦点进入/返回、Esc 关闭和清晰的可访问名称。所有异步操作有 loading、empty、partial、error 状态。

## Risks / Trade-offs

- [现有创建/删除/元数据 API 是直接写入] → 先盘点其目标文件、冲突检查和恢复逻辑，再在同一后端写入路径前增加准备/预览阶段；相关任务先于界面启用审核入口。
- [Provider 切换或刷新导致草稿丢失] → 将草稿状态置于稳定的项目工作区层；离开时提示并保留本次会话草稿，不将草稿当作已应用内容。
- [右侧面板压缩文章] → 根据窗口宽度使用覆盖抽屉，始终保留文章最小可读宽度。
- [偏好存储与项目重新定位] → 仅存稳定项目 ID；项目移除或页面消失时清理/忽略悬空引用。
- [概念图展示了尚无数据源的指标] → UI 只展示真实契约字段；缺失信息显示“未知”或移除该项。
- [大型 Reader 重构影响现有行为] → 按视图逐步迁移并复用 service 接口；覆盖双 Provider、搜索直达、未保存草稿、外部改动和历史恢复的主路径测试。

## Migration Plan

1. 固定当前主路径的自动化基线；定义应用壳层和 token，保留原有 service 边界。
2. 将首页与项目库分开并引入显式导航；已有项目数据和收藏不迁移。
3. 把 Reader 移入项目工作区，接通跨项目搜索定位和独立 Provider 会话；旧 UI 可在开发阶段并行保留，最终删除冗余入口。
4. 完成维护预览所需契约，再切换新增/编辑/删除/元数据/AI 的审核界面；验证原文件、历史及冲突结果。
5. 完成窗口宽度和键盘回归后移除长页面布局。若 UI 发布回退，回退前端视图即可；若已引入新的 ChangeSet 契约，旧界面继续调用兼容服务，已应用的原文件和历史不得回滚。

## Open Questions

- 当前持久化层是否已有适合阅读偏好的接口？实施首项任务先核对；若没有，用仅存非敏感 ID 的本地偏好存储并验证升级保留行为。
- 多文件 ChangeSet 的通用结构及是否包含新增/删除文件，需在拆分直接写入接口时以真实操作样例确定；界面契约至少要列出每个受影响文件和校验结果。
